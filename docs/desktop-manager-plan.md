# OIH 管理程序方案 (V0.1)

## 1. 背景与目标

当前 OIHelper 的配置分散在 VS Code settings、工作区文件和命令行参数中, 缺少统一入口。本方案新增一个独立的 Electron 桌面程序, 作为本地/远程服务器、凭据、工作区的管理中心, VS Code 扩展通过 WebSocket 接入。

目标:

- 统一管理本地评测服务与远程 OIH 服务
- 统一管理各 OJ 的多账号凭据, 并支持与工作区双向同步
- 自动识别本机 OIH 工作区与服务实例, 识别不到的允许手动添加
- 不改变现有评测流程, 仅新增管理入口

## 2. 总体形态

- **Electron 桌面程序**: 单实例常驻, 支持托盘与开机自启
- **内置 WebSocket 服务**: 扩展连接后上报工作区与状态, 程序下发指令
- **端口策略**: 默认固定端口 `17321` (可配置); 端口被占用时改用随机端口, 并写发现文件
- **发现文件**: `%APPDATA%/OIHelper/agent.json`, 内容为 `{ "port": 17321, "token": "...", "pid": 1234, "version": "V0.1" }`
- **鉴权**: 所有消息携带 token, 由发现文件下发

扩展连接顺序: 先连配置的固定端口, 失败后读取发现文件重试。

## 3. 页面结构

顶部 tab: **服务器 / 识别到的OIH / 凭据 / 接口 / 工作区 / 设置**, 默认落在服务器。

### 3.1 服务器

「本地」「远程」两个子页签, 标题带数量徽标; 顶部一行概览显示当前默认连接。

**本地服务器**

| 列 | 说明 |
|---|---|
| 名称 | 自定义 |
| 地址 | `host:port` |
| 访问方式 | 本机 / 局域网 / 公网 |
| 域名组 | 公网访问时选择 |
| 状态 | 运行中 / 已停止 |
| 操作 | 启动 / 停止 / 编辑 / 删除 |

- 新建本地服务器时可「添加域名组」, 一组记录多个常用域名
- 公网访问必须填写域名; 局域网可只填 IP

**远程服务器**

| 列 | 说明 |
|---|---|
| 名称 | 自定义 |
| 地址 | 服务 URL |
| 连接状态 | 已连接 / 未连接 / 连接失败 |
| 我的权限 | 自定义标签, 创建时填写, 后续可修改 |
| 操作 | 连接 / 断开 / 编辑 / 删除 |

- 新建时先选类型 (本地 / 远程)
- 远程连接需填写地址与验证信息

### 3.2 识别到的OIH

两张表 + 一键对照。

**工作区表**

列: 工作区 / 路径 / 服务器连接 (内联状态点) / 状态。

- 支持多选、JSON 管理、新建工作区
- 识别规则: 目录含 `.oihelper/workspace.json` 或 `problems/` 即视为 OIH 工作区

**服务实例表**

列: 来源 / 地址 / 版本 / 状态 / 关联工作区数。

来源取值:

- 程序启动: 程序自己拉起的实例, 端口直接登记
- 扩展上报: 扩展连接后上报当前使用的服务
- 扫描: 探测本机已知端口
- 手动: 用户填写地址后探测成功

扫描策略: 程序启动登记的端口 + 本机常用端口探测; 不做全端口段扫描与局域网广播。识别不到的走手动添加。

**一键对照**

选中工作区后右侧展开实例表, 双向高亮绑定关系; 再次点击关闭, 回到单视图。

### 3.3 凭据

- 按 OJ 分组 (xmoj、洛谷、Codeforces、AtCoder、Hydro 等), 下拉框分组展示
- 每个 OJ 支持多条账号条目: 用户名 / 密码 / Cookie / 备注 / 是否默认
- 总存档路径可配置, 所有工作区共用
- 每个工作区显示同步状态: 已同步 / 有差异 / 未同步
- 同步前先比对, 然后三选一:
    - 不做改变
    - 工作区配置写入存档
    - 存档写入工作区配置
- 自动同步模式:
    - 关闭
    - 单向: 工作区 → 存档 (存档变化不影响工作区)
    - 单向: 存档 → 工作区 (工作区变化不影响存档)
    - 双向
- 同步粒度为按条目合并, 冲突逐条选择

### 3.4 工作区

本期为空态占位, 后续补充。

### 3.5 设置

- 总存档路径
- WebSocket 端口
- 开机自启
- 托盘开关
- 扫描端口列表
- 自动同步默认模式

### 3.6 接口

统一管理程序对外暴露的三类调用入口。

| 子页签 | 内容 |
|---|---|
| API | 监听地址、端口、开关、令牌、请求日志 |
| CLI | 可执行文件路径、是否加入 PATH、命令列表与示例 |
| MCP | 服务开关、传输方式、已连接客户端、工具清单 |

- API 与 MCP 共用同一份令牌, 在凭据 tab 之外单独管理
- 每个入口提供「测试调用」按钮, 结果显示在下方日志区
- 危险操作 (删除服务器、覆盖同步) 在 API 层默认关闭, 需显式开启

## 5. 工作区目录结构

```text
<workspace>/
    .oihelper/
        workspace.json      # id / name / serverId
        credentials.json    # 凭据快照
    problems/
```

## 6. 同步机制

- 存档与工作区各自保存一份 `credentials.json`
- 比对键: `oj + username`
- 差异判定: 同一键的密码、Cookie、备注任一不同, 或仅存在于一侧
- 手动同步: 展示差异列表, 整体三选一或逐条选择
- 自动同步: 按设置的方向执行, 冲突条目暂停并提示

## 7. 扩展与程序通信

消息格式:

```json
{ "type": "hello", "token": "...", "payload": {} }
```

扩展 → 程序:

- `hello`: 版本、工作区路径
- `status`: 当前服务器、连接状态
- `credentialsChanged`: 工作区凭据文件变化

程序 → 扩展:

- `openWorkspace`: 打开指定目录
- `createWorkspace`: 在指定目录创建工作区结构
- `syncRequest`: 触发同步
- `ping`: 保活

## 8. 服务端改动

现有 `oi serve` 只提供 `POST /judge`, 新增:

```text
GET /health -> { "name": "oi-helper", "version": "V0.1", "status": "ok" }
```

用于扫描探测与版本列展示。

## 11. 平台层: API / CLI / MCP

程序不再只是管理器, 同时是 OIH 的对内调用入口。三者共用同一套服务实现, 只是外壳不同。

| 层 | 形态 | 命名 | 说明 |
|---|---|---|---|
| 服务 | 进程内模块 | `oihd` | 服务器、凭据、工作区、评测状态的核心逻辑, 只此一份 |
| API | HTTP REST | `http://127.0.0.1:<port>/api/...` | 供外部脚本、其他工具调用 |
| CLI | 命令行 | `oih` | 仿 lark-cli: `oih server list`、`oih sync push`、`oih judge run` |
| MCP | stdio + HTTP | `oi-helper-mcp` | 服务由程序托管, 不再是独立进程 |
| GUI | Electron | 管理面板 | 上面四层的人工操作界面 |

约束:

- 现有 `oi-judge` 是评测内核, 保持不变; `oih` 是管理层 CLI, 两者不合并, 避免评测逻辑受管理逻辑影响
- 现有 `mcp/server.js` 合并进程序, 保留对外工具名不变
- CLI 输出格式与 lark-cli 对齐: 默认 JSON 信封 `{ ok, identity, data, error }`, 成功以 `ok == true` 判断
- CLI 的写操作与高风险操作需要显式确认参数, 与 lark-cli 的确认机制一致
- API / CLI / MCP 的权限在接口 tab 内统一配置, 默认只开读操作

## 12. 扩展能力: 环境准备与错误修复

### 12.1 C++ 考试环境准备

范围定义: OI 考试时用到的全部环境, 不涉及第三方库管理。

检查项:

- 编译器: g++ 是否存在、路径、版本
- 标准: 实际生效的 C++ 标准 (14/17/20)
- 头文件: `bits/stdc++.h` 是否可用、include 路径
- 运行环境: 终端编码、栈大小、时间精度
- 模板: 代码模板与快读快写片段

操作:

- 一键体检, 列出缺失项与建议
- 一键生成/修正编辑器配置 (参考 `D:\biglab\cpp` 的 `c_cpp_properties.json`、`tasks.json`、`launch.json`、`settings.json`)
- 一键写入代码模板

### 12.2 自动查错与修复

按成本从低到高实现, 每条都先给提示, 再提供「一键修复」。

| 错误 | 检测方式 | 修复动作 |
|---|---|---|
| YES 写成 Yes, 或反之 | 全文大小写比对 | 一键替换 |
| 缺少文件输入输出 | 已有 freopen 扫描 | 一键在 main 开头插入 freopen |
| 除以 0 或模 0 | 定位除号右操作数 | 一键补判断分支 |
| 缺少分号 | 编译错误行号 | 一键在报错行尾补分号 |
| 其他常见编译错误 | 规则库匹配报错文本 | 给修复建议, 不自动改 |

- 修复前展示待改片段, 用户确认后写入
- 无法定位时只给建议, 不猜测改写

### 12.3 OIWiki 接入

- 提供题解与算法知识检索, 结果面板展示标题、摘要与原文链接
- 支持在编辑器里对算法关键词做补全, 补全项来自本地建立的 OIWiki 索引
- OIWiki 内容为 CC BY-SA, 展示时必须保留来源标注与原文链接, 不整段复制到用户代码

## 13. OICPP / Dev-C++ 置顶悬浮窗

- 独立窗口, 无边框、可置顶、可拖动缩放, 尺寸与位置记忆
- 显示: 当前题目、测试点列表与状态、评测结果、提交结果
- 操作: 一键评测、切换测试点、打开题目
- 源码编辑仍在 OICPP / Dev-C++ 内完成, 悬浮窗只做展示与触发
- 与主程序共用同一份服务端逻辑, 悬浮窗作为第二个渲染入口, 不重复实现评测

## 14. 界面规范

- 桌面程序与悬浮窗: 仿飞书设计, 中性色背景、圆角卡片、分组留白
- VS Code 扩展面板: 继续跟随编辑器主题色, 不套用飞书配色
- 两套界面只在颜色与排版上不同, 信息结构和字段命名保持一致

## 15. 浏览器扩展: 采集层

用浏览器里已有的登录态完成抓取, 与 Node 端抓取共用同一套解析层, 不重复实现。

| 能力 | 说明 |
|---|---|
| 路由爬虫 / 网页请求 | 后台 `fetch` 携带站点 Cookie, 绕开跨域限制 |
| 一键获取 Cookie | 通过 `cookies` 权限读取, 包含 HttpOnly |
| 代理 | 只允许用户填写自己的代理地址, 不内置, 不做共享 |
| 自动识别 OJ 界面 | 域名 + 关键 DOM 特征匹配, 规则按站点版本化 |
| 自动填充账号密码 | 密码本地加密存储, 默认关闭, 开启需确认 |
| 获取完整页面 | 取 `document.documentElement.outerHTML` 交给解析层 |
| 验证码自动识别 | **默认关闭**; 开启时弹出风险警告, 持续 5 秒, 明确由用户承担风险; 可设置对哪些 OJ 生效 |
| 手动分析界面 | 用户点选元素生成选择器, 作为站点改版后的兜底 |

- 验证码与自动填充均需显式开关, 且只在用户本人已登录的浏览器内生效
- 采集结果统一转换为题目对象, 与现有抓取结果同构

## 16. 局域网协作与通知

聊天与通知由局域网服务器承载, 不依赖公网服务。

- 服务器角色: 消息中转、在线状态、可选消息留存
- 工作区聊天: 简易实时聊天, 类飞书的消息列表与输入框, 只在同一局域网服务器内可见
- 比赛通知: 队友提交了第几题、谁拿到一血、封榜与解榜等事件
- 通知落点: 桌面程序托盘通知、扩展侧提示, 两处共用同一事件源
- 开放接口: 事件以统一结构暴露, 用户可自行配置订阅哪些事件、如何提醒
- 与 ICPC 赛制、榜单轮询逻辑共用数据源

## 17. 分发

- 单个 `.exe` 安装包, 一次装好桌面程序与扩展
- 安装时探测本机编辑器: VS Code、Trae CN 等
- 自动安装扩展: 调用编辑器自带的 `--install-extension`, 失败时回退到扩展目录复制
- 任一方式失败时, 提供 `.vsix` 与手动安装说明, 不静默失败
- 在线 IDE 无需安装, 由浏览器扩展承载

## 18. 在线 IDE 支持

- 浏览器扩展在在线 IDE 站点内注入侧边面板
- 面板能力与 VS Code 扩展一致: 题目信息、测试点、评测、提交、结果查看
- 编辑能力交给在线 IDE 自身, 不自建编辑器
- 站点适配按"一个站点一个适配器"处理, 与 OJ 适配器分开维护
